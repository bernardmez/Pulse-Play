SLIDE 2 — What is Pulse Play? 1 minute 
The Problem
  Users need a centralized platform to discover, stream, and organize music

The Solution — Pulse Play
  ✦ Search songs by title, artist, genre, album
  ✦ Full playback controls — play, pause, skip, shuffle, repeat
  ✦ Personal playlists, liked songs, listening history
  ✦ Personalized recommendations based on listening behavior
  ✦ Artist profiles and album browsing

Two user roles:  Regular User  ·  Administrator
Stack:           React  ·  Node.js  ·  MariaDB
Say: "Pulse Play is a database-driven web application. Users register, search for music, play songs, build playlists, and receive recommendations based on their listening history. We identified two roles in our SRS: regular users who consume music, and administrators who manage the catalog. The stack is React on the frontend, Node.js with Express on the backend, and MariaDB as the relational database."

SLIDE 4 — Database Design 2 minutes 
9 Tables — from SRS Section 3.1.2

  users                   user accounts and subscription type
  artists                 music creators with follower counts
  albums                  grouped releases by artist
  songs                   catalog: play_count, likes_count, audio_url
  playlists               user-owned collections
  playlist_songs          many-to-many: playlists ↔ songs + position
  user_favorites          liked songs per user
  user_following_artists  followed artists per user
  listening_history       every play event with timestamp + duration
  subscriptions           plan records with start/end dates

3 Views
  artist_statistics       aggregates total plays, songs, albums per artist
  user_playlist_details   playlists with total_tracks and total_duration
  active_subscriptions    subscriptions where end_date >= today

5 Stored Procedures
  add_song_to_playlist        position calculation + total_tracks update
  remove_song_from_playlist   delete + recalculate duration atomically
  record_song_play            INSERT history + UPDATE play_count
  get_user_recommendations    genre/artist matching from history
  update_user_subscription    create record + sync user plan

Key Relationship: playlist_songs (SRS Rule 4 — many-to-many)
  → position column maintains song order within playlist
  → stored procedure ensures total_tracks is always consistent
Say: "Our database has 9 tables that map directly to the entities defined in Section 3.1 of our SRS. The most important design decision is the playlist_songs junction table — it resolves the many-to-many between playlists and songs and adds a position column for ordering. Rather than handling this in application code, we put the logic in stored procedures. Adding a song calls a procedure that calculates the next position, inserts the record, and updates total_tracks atomically in one database call."

SLIDE 8 — Challenges & Lessons 1.5 minutes 
Most Significant Challenge: Integration

What blocked us:
  ✗ dotenv never loaded    → backend crashed on every startup
  ✗ API URLs hardcoded     → breaks outside one specific machine
  ✗ No schema.sql in repo  → nobody could run the project independently
  ✗ Missing PUT route      → Edit Playlist silently failed in frontend
  ✗ Token expired in 15min → Library tab showed blank screen

How we resolved each one:
  ✓ Added import 'dotenv/config' to env.js
  ✓ Changed all URLs to relative /api/ paths (Vite proxy handles routing)
  ✓ Created complete schema.sql — tables, views, procedures, seed data
  ✓ Added PUT /api/playlists/:id route
  ✓ Extended JWT to 24h, added Array.isArray guard on all fetches

Lesson:
  "Integration is not automatic. It needs its own sprint."
Say: "Our biggest challenge was integration. Each piece worked separately but connecting them revealed five blockers — dotenv not loading, hardcoded URLs, no SQL schema in the repo, a missing route, and an expiring token. Each had a targeted fix. The lesson: integration needs to be a deliverable from sprint one, not assumed to work at the end. I'll hand to Mohamad for the architecture."

SLIDE 3 — System Architecture 2 minutes 
┌──────────────┐   /api/* requests   ┌────────────────────────┐
│    React     │ ──────────────────► │    Express API         │
│  Frontend    │ ◄────────────────── │    Node.js :5000       │
│   :3000      │   JSON responses    │                        │
└──────────────┘                     │  Helmet  (sec headers) │
                                     │  CORS    (allowlist)   │
                                     │  JWT     (auth layer)  │
                                     │  Zod     (validation)  │
                                     │  Rate    (limiter)     │
                                     │  13 Route files        │
                                     └───────────┬────────────┘
                                                 │ SQL + Stored Procedures
                                     ┌───────────▼────────────┐
                                     │   MariaDB  :3306       │
                                     │   9 Tables · 3 Views   │
                                     │   5 Stored Procedures  │
                                     └────────────────────────┘

Why these choices:
  React    → component model matches modular SRS (NFR-MAINT-001)
  JWT      → stateless, supports 100+ concurrent users (NFR-SCAL-001)
  MariaDB  → FK constraints enforce data integrity (NFR-REL-003)
  Zod      → input validation at API boundary blocks bad data
Say: "The system is three-tier. React on port 3000 never talks to the database directly — all requests go through the Express API on port 5000, which is the only layer that touches the database. This satisfies NFR-SEC from our SRS. Inside the API, five middleware layers run on every request before reaching one of 13 independent route files. We chose JWT because it is stateless — the server holds no session state, allowing the system to handle 100+ concurrent users as required by NFR-SCAL-001."
